# Changelog

## 1.1.0 — 2026-10-27

- **New public API for native screens: `AttachmentProcessor` (iOS framework + Android aar)** — the "after picking" processing that used to live only inside the RN bridge (photo resize and save as webp / jpg / png, photo thumbnail, video export with `VideoExporter` and its poster, the processing-start slots with predicted sizes and posters, progress throttling, per-video cancel, temp files and the result model). An app's own native screen can now open the kit gallery and process the result with exactly the same code as `openGallery`, so both produce the same files (size, thumbnail, poster).
  - iOS: `AttachmentProcessor.process(_:videoStates:options:job:onStart:onVideoProgress:onItem:)`, `startItem`, `processPhoto`, `processVideo`, and the helpers (`resizeImage`, `saveImage`, `encodeWebP`, `makePhotoThumbnail`, `photoThumbnailLayout`, `videoFrame`, `requestPoster`, `prepareCacheDirectory` …). Models `AttachmentProcessingOptions`, `AttachmentStartItem`, `AttachmentResult` (`.dictionary` = the RN result fields), `AttachmentProcessingJob` (`cancel(index:)` / `abort()`), `AttachmentProgressThrottle`; `PhotoThumbnailOptions` is now public.
  - Android: `com.rnattachmentkit.AttachmentProcessor` (`process` / `processPhoto` / `processVideo` are `suspend`), `Options`, `Result` (`toMap()` = the RN result fields), `Listener`; `ProcessingJob.abort()` / `isAborted`.
  - The RN bridge (`openGallery` on both platforms, iOS `openEditor` video / photo paths) now calls these — no change in the JS API, events or result fields. The progress HUD's cancel is `job.abort()` (whole send cancelled, Promise rejected as before).
- **Android: the aar is exposed to the app (`api`)**, together with `material` and `media3-transformer` (supertypes / signatures of public classes). An app's native code can use the kit classes without its own `compileOnly` copy of the aar. Class names are kept by the aar's `-keep class com.rnattachmentkit.** { *; }`; apps that minify keep the same rule in their `proguard-rules.pro` (HeyTalk / ZemTalk already do).
- **License: `LicenseManager.isInitialized` and `whenInitialized(timeout:)` (iOS + Android)** — lets a native screen wait for the RN side's `AttachmentKit.init` before it opens the gallery or processes anything (the gallery's video permission and the photo watermark read the license).
- Checked in HeyTalk (new devices `HeyTalk_KIT` simulator / emulator, one batch of a 4032×3024 jpg + a 1080p 6 s mp4): on iOS and on Android the RN `openGallery` path and the app's native chat room produced byte-identical photo webp (1024×768), processing-start poster and export poster, and mp4s with the same codec, size, duration, frame count, bitrate and byte count (only the mp4 creation time differs). An Android photo bug introduced while moving the code (bounds-only decode treated as failure, so every photo was dropped) was found by that check and fixed before this build. ZemTalk: iOS device build (no signing) and Android Kotlin/Java compile pass with no change to ZemTalk.

## 1.0.18 — 2026-10-23

- **Image viewer (iOS) and full-screen camera (iOS + Android): pull-down follows the finger back up freely**, like the editor. Before, dragging down and then back above the starting point made the photo / camera stop at a fixed height.
  - iOS viewer: the "drag started upward" check looked at `view.transform`, which never moves (the photo is `scrollView`), so every upward move was skipped. It now checks `scrollView.transform`, the same rule as the editor (`collectionView.transform`).
  - iOS camera: the vertical move was clamped with `max(0, translation.y)`; the camera now follows `translation.y` (scale like the editor). Fade, corner radius and the close decision still use only the downward distance.
  - Android camera: `translationY` used the clamped pull; it now follows `dy * 0.7` up and down like `PullToDismissLayout` (editor / viewer). Scale and fades still use only the downward distance.
  - iOS typecheck and Android module compile. Not tried on a device or simulator yet (the simulator was in use by another app).

- **Viewer: closing a video page cross-fades to the chat thumbnail while it flies back (iOS + Android)**. The close animation flies the current video frame back to the message; at the end the message's own thumbnail (the poster) appeared in one frame, which looked like a flash when the video had moved on from the first frame. Now the poster is laid over the frame inside the flying image, transparent, and fades in during the middle of the animation (15% → 75% of the close), so it arrives as the thumbnail. iOS: a poster `UIImageView` inside `ZoomTransitionAnimator`'s dummy view (poster from the page's image view, else the memory cache). Android: `dismissViewer` passes a `LayerDrawable` [frame, poster copy] to `playCloseAnimation` and raises the poster layer's alpha in the animator. Pull-down close and button close both use it; photo pages are unchanged.
  - iOS framework build (simulator) and Android module compile. Not tried on a device yet.

- **Android full-screen camera: a second finger during pull-down no longer leaves the camera stuck mid-drag**. Touching with another finger while dragging the camera down turned the drag off (as if a pinch started) without putting the camera back, so after lifting the fingers it stayed shrunk where it was. While dragging, extra fingers are now ignored (no pinch zoom) and the camera keeps following the finger that started the drag; lifting that finger (or all fingers) finishes the drag as usual — closes if pulled down far enough, otherwise springs back. Drag / release code moved into `dragTo` / `finishDrag`. iOS was not affected (its pan takes one touch and ends on `.cancelled` too).
  - Android module compile. Not tried on a device yet.

- **iOS viewer: no dark flash when a video starts playing, and it starts as soon as possible**. The poster → video fade (1.0.17) put a black background on the player layer as soon as `isReadyForDisplay` was true, but the layer can go blank for a frame or two right when playback actually begins; the black background then showed through the half-faded video and the poster dimmed for a moment (sometimes, depending on whether the first frame was ready before playback started). Now the poster always stays behind and the video fades in over it the moment the first frame is ready, with no background — a blank frame just shows the poster. Only once frames are clearly on screen (the play position moved about 0.05 s, or the player is paused, or 1.5 s passed) and the fade has finished (+0.2 s) does the black background come in (0.2 s) to hide the poster where its aspect differs from the video. Re-attaching the player that is already shown (back to the same page) no longer hides it and fades it in again.
  - iOS framework build (simulator). Not tried on a device or simulator yet.

- **Viewer: `startWithUiHidden` option (iOS + Android overlay viewer)**. Opens the viewer with the top bar, bottom bar and video controls hidden — a tap shows them (and, while a video plays, they hide again after 3 s as before). While the UI is hidden the centre button still appears when the video is stopped (▶) or loading / downloading (spinner, ring), but not during the open animation before autoplay starts, and the loading spinner only after 0.4 s of loading (a cached file buffers for a moment and starts — the spinner used to pop up and fade out showing ⏸). When loading ends while the UI is hidden and the video plays, the button fades out without revealing ⏸. Android: dragging the viewer and letting go no longer brings hidden bars back to their place invisibly (their close / save buttons stayed tappable).
- **Viewer video controls stay up while a save / share / delete menu is open (iOS + Android)**. The controls auto-hid 3 s after playback started even while the "save all / this video" or "share all / this video" chooser, the delete confirmation or the share sheet was open, so the top bar slid away and took the chooser anchored to its button with it (iOS: the popover moved up under the status bar). The 3 s timer now waits while the viewer is in use — scrubbing, the speed menu, anything the viewer presents (iOS `presentedViewController`; Android: the viewer window has lost focus to a popup, dialog or the share chooser), or a save / share still fetching its items (download HUD) — and starts counting again once that ends (`isVideoUiInUse` / `waitUntilVideoUiIdle` on iOS, `isUiInUse` / `waitUntilUiIdle` on Android). Photo pages have no auto-hide, so nothing changes there.

## 1.0.17 — 2026-10-22

- **Viewer: a remote video is downloaded once, not twice (iOS + Android)**. The player streamed the video while a separate background download fetched the same file for the cache (`cacheFile`), so every first view used twice the data and the two downloads slowed each other down.
  - Now only the background download fetches the file, writing to `<cacheFile>.part` as it arrives, and the player reads that growing file: it waits where the download has not arrived yet (the center ring / bar show it), and only a request far past the downloaded part (a `moov` at the end of the file, or a seek far ahead) is fetched separately with an HTTP range request. If the download fails, the player continues from where it is with range requests.
  - Android: `ViewerStreamDataSource` (Media3 `DataSource` over `ViewerVideoDownload`), used through `ProgressiveMediaSource` when the page has a `cacheFile`. iOS: `ViewerStreamLoader` (`AVAssetResourceLoaderDelegate` on a custom-scheme `AVURLAsset`); `ViewerVideoFiles` now uses a data task that writes the `.part` itself (the download task's temp file could not be read while downloading).
  - A download that ends short of `Content-Length` now counts as failed (it used to be saved as complete).
  - Removed in 1.0.15's "switch to the downloaded file if it finished before playback started" — no longer needed.
- **Viewer: the progress bar can only be dragged over the downloaded part while a video is downloading (iOS + Android)**. Seeking into a part that had not arrived yet left the player waiting there with no feedback. The thumb now stops at the downloaded fraction (2% inside, since bytes ≈ time); once downloaded, or for local / non-cached videos, there is no limit.
- **iOS: the video fades in over the poster after the viewer opens (no flash)**. The video layer used to replace the poster in one frame on the first decoded frame — most visible with HDR videos (iPhone HLG), which iOS shows with HDR brightness, so the picture jumped brighter than the SDR poster. The video still plays as the original (HDR stays HDR); only the switch is smooth: the player layer stays hidden until the first frame is ready, then fades in over 0.35 s. The open animation is unchanged (playback still starts in `viewDidAppear`).
- **Viewer video options pill: playback-speed icon, first on the left (iOS + Android)**. The ⚙ button (it only opened the playback-speed menu) now shows a speed icon (iOS `speedometer`, Android `ic_viewer_speed` — Material "speed") and is the leftmost button: speed · mute · (HDR) · fullscreen.
- **iOS viewer: HDR on/off button for HDR videos**. Shown in the options pill only when the video track is HDR (`containsHDRVideo` or HLG / PQ transfer function). On (default) plays the original HDR; off plays it with SDR (BT.709) brightness through a `videoComposition`. The choice applies right away and is remembered (`UserDefaults` `RNAttachmentKit.viewerVideoHDR`). The video stays hidden behind the poster until this is decided, so an "off" video never flashes HDR. If the SDR composition makes playback fail (seen on the iOS Simulator; on macOS the same composition plays and toggles fine), the viewer drops it, continues the original from the same position and hides the button for the rest of the app run (`ViewerVideoHDR.compositionUnsupported`). Switching while playing used to flash and jump back to the previous key frame (changing the composition re-prepares the player); now the current frame is laid over the video (keeping its old brightness), playback continues from exactly the same time (zero-tolerance seek) and the overlay fades out over 0.35 s once the new frames are on screen (`switchVideoHDR`). Android has no button (its TextureView already shows HDR videos at SDR brightness).
- **Viewer video controls don't hide while you use them (iOS; Android touch-up)**. iOS: the controls auto-hid 3 s after playback started even while the playback-speed menu was open or the pill buttons were being tapped. Every touch on a pill button now restarts the 3 s timer (`ViewerVideoControlsView.onInteraction`), and nothing hides while the speed menu is open (`ViewerMenuButton` reports menu open/close; the timer restarts when it closes). Android already kept the controls while its speed menu was open; opening the menu now also restarts the timer.
- **Video poster = first frame of the sent video (iOS + Android)**. iOS `onProcessingStart` used the gallery thumbnail (the Photos key frame, not always the first frame) when the video was not trimmed; it now always reads the frame at the (trimmed) start. Export thumbnails are taken exactly at 0 s (iOS: zero tolerance instead of the nearest key frame around 0.1 s; Android: `OPTION_CLOSEST` instead of `OPTION_CLOSEST_SYNC`, which also affected the trimmed-start poster).

## 1.0.13 — 2026-10-21

- **iOS: crash closing the picker — `-[AVCaptureSession stopRunning]` exception (Crashlytics, `closure #1 in CameraPreviewView.stopPreview()`)**.
  - Cause: the gallery camera does all session work (start, stop, recording formats) on one serial queue, but the full-screen camera's front/back flip changed the session on its own queue (`com.overlay.camera.q`). If the picker closed while a flip was inside `beginConfiguration … commitConfiguration`, `stopPreview` called `stopRunning` mid-configuration and AVFoundation threw.
  - The flip now runs on `CameraPreviewView.sharedSessionQueue` (made internal; the separate queue is gone), so every start / stop / configuration of the session is serialized. No other code touches the session outside that queue.
  - Typecheck only (the simulator has no camera to reproduce the race).
